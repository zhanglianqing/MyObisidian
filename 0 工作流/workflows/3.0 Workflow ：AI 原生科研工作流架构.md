## 1. 核心存储与同步策略
我们将科研资产分为四类，通过统一的目录结构进行管理：

> **需求前提（2026-05）**：日常问答以 **Obsidian Copilot + Zotero LLM** 为主，对 **网页版 Gemini / NotebookLM** 的依赖下降；Obsidian 与 Zotero 附件的**主力同步**改为 **坚果云**（国内链路更省流量、双机更及时）。**Google Drive** 保留为**按需**（VPN + 暂停/恢复），不再作为整库实时底座。

| 资产类型             | 存放位置          | 推荐工具               | AI 调用方式                                                    |
| :--------------- | :------------ | :----------------- | :--------------------------------------------------------- |
| **影像数据 (Data)**  | data/         | 软链接                | **本地 HDD**                                                 |
| **笔记 (Notes)**   | `notes/`      | Obsidian           | **坚果云**（实时同步 vault 所在目录）                          |
| **文献 (Lit)**     | Zotero PDF + `7 可复用知识库/literature/` | Zotero + Citations | **坚果云**同步 PDF；内化笔记平面存放（见 [[0 工作流/workflows/3.8 Workflow ：文献库组织架构]]）   |
| **代码 (Src)**     | `code/`       | Git / Cursor       | `@Codebase`；**Git 远程仓库** (GitHub/GitLab)                   |
| **结果 (Results)** | `results/`    | Obsidian           | **坚果云**（与 vault 同盘同步）；**Git 远程仓库** (GitHub/GitLab)实现版本管理 |
| **输出**           | manu/         |                    | **坚果云**（与 vault 同盘同步）；**Git 远程仓库** (GitHub/GitLab)实现版本管理 |

### 1.1 迁移到坚果云（Obsidian + Zotero）操作顺序

1. **坚果云**：在客户端中确认 vault 与 Zotero `literature` 根目录都在「已同步」路径下（可为同一磁盘上的两个同步文件夹，或统一放在同一父目录下由坚果云一并同步，以你客户端里实际勾选的同步根为准）。
2. **Obsidian**：退出 Obsidian → 将整个库文件夹（含 `.obsidian`）**剪切**到坚果云同步目录内 → 重新用 Obsidian「打开该文件夹作为库」。第二台机待坚果云**完全同步**后再打开同一库路径。若 Cursor 曾把本库加入 **Index**，迁移后改为新路径下的同一文件夹。
3. **Zotero**：将原链接附件目录（如 `L:\zotero\literature`）整体迁入坚果云同步路径下 → 在两台机分别把 **Attanger 靶路径** 与 **首选项 → 高级 → 文件和文件夹 → 链接附件的根目录** 改到新路径（盘符可不同，但相对结构一致）。详见 [[3.1 Workflow ：Zotero+Obsidian 文献由进到出全流程]]。
4. **收尾**：原 Google Drive 本地镜像里若仍有旧 vault / `literature` 副本，在确认坚果云侧无误后，从 Drive 同步中移除或删除本地副本，**避免**同一内容被坚果云与 Drive **双客户端长期抢写**。

### 1.2 Google Drive 桌面版改为「按需」（手动触发）

Drive for desktop **没有**「整账户仅手动点一次才双向同步」的独立模式，可用下面组合达到「平时不占 VPN、需要再拉」的效果：

- **暂停 / 恢复同步**：托盘 **Google Drive** 图标 → **设置（齿轮）** → **暂停同步**；需要与云端对齐时再 **恢复同步**。暂停期间本地改动会在恢复后排队上传（以官方客户端行为为准）。
- **缩小镜像范围**：若仍保留部分目录在 Drive 上，在偏好设置里**只勾选**仍需上云的小范围文件夹；大库与 PDF 已迁出坚果云后，Drive 只做归档或协作用。
- **偶发需求**：网页版 Gemini / NotebookLM 需要时，再对**单文件或导出包**上传即可，不必维持整库常驻 Drive。

## 2. 深度版本化项目结构 (Project Anatomy)
每个科研项目（如 `01_Memory_TMS`）应作为一个独立的 **Git 仓库**，结构如下：

```text
Project_Name/
├── .cursorrules          # AI 身份与项目全局背景
├── .gitignore            # 忽略临时文件与环境
├── README.md             # 项目总体概况与当前阶段目标
├── RESEARCH_TRACKER.md   # 【核心】实验追踪器：记录探索分支与结论
├── notes/                # Obsidian 主要活动区 (双向链接)
├── literature/           # 【独立 Git 仓可选】代码仓内文献笔记；vault 级见 7 可复用知识库/literature/
├── data/                 # 原始数据及中间过程文件保存区，仅本地(不上传任何地方)，软链接供查阅
├── code/                  # 项目
│   ├── main               # 稳定版本的主处理流程
│   ├── main_results/      # 主线结果，用于report，通过git实现版本迭代 
│   └── explore_experiments/      # 存放独立的探索性脚本及相应结果，每次单独开文件夹，通过git实现版本迭代(如 exp_v1_grad.py)             
└── manu/                 # 成品稿件，word文档供投稿 (通过git实现版本迭代)
```

### 3.4 Git 版本管理

- **Vault 级仓库（2026-06-06 定稿）**：`https://github.com/zhanglianqing/MyObisidian` · 分支 `main`。
- **双通道同步**：
  - **坚果云** → vault 正文（md、配置、小图）双机实时同步；
  - **Git** → 版本历史 + GitHub 远端备份；**Git 对象库不进坚果云**。
- **本机布局**：
  - vault 内 `.git` 为**指针文件**（约几十字节，可随坚果云同步）；
  - 对象库在 `%USERPROFILE%\.local\git\MyObisidian.git`（每台机器本地一份）。
- **首台 / 第二台机器**：`0 工作流/scripts/Setup-VaultGit.ps1`（指针里的 GitStore 路径**按本机用户**写入，勿手改）
  - **主力机** `LAPTOP-HMRRC11`（`E:\Obisidian\MyObisidian`）：已 `-Relocate`；日常 `git pull` → 改 vault → `commit` → `push`
  - **笔记本** `lilianna-usus`（`C:\Users\41516\Nutstore\1\MyObisidian`）：坚果云同步 vault 后执行  
    `.\Setup-VaultGit.ps1 -Bootstrap -VaultPath "C:\Users\41516\Nutstore\1\MyObisidian"`  
    并在本机配置 GitHub 凭据（HTTPS token 或 SSH）
- **双机分工**：坚果云 = 工作区实时同步；Git = 版本检查点 + GitHub 备份。换机开工前先 `git pull`，收工有 checkpoint 则 `push`。
- **追踪范围**：项目数据（含 PDF/DOCX/PPTX、定稿、审稿材料等）**保留**在 Git；**不**版本化 `Clippings/`、邮件 drop / 待整理队列、密钥与本地状态。见根目录 `.gitignore`。
- **子项目仓**：仍可在各项目文件夹（如 `01_Memory_TMS/`）下单独 `git init`。
- **注意：** Obsidian 不介意子文件夹里有 `.git`。避免同一目录再被 Drive 实时镜像，以免双客户端竞态。

- **写作/改稿版本原则（2026-06-04）：** vault 活跃区只保留当前工作版；大改版前后用 Git checkpoint 留细颗粒历史，本地硬盘/坚果云原工作流目录保留原始多版本材料。不要把 `v1/v2/旧版/新版/finalManu` 过程稿整包搬进 vault，以免 AI / agent 把历史稿误判为当前依据。

## 4. 三阶段操作循环 (The Research Loop)

1. **输入期**：更新 `RESEARCH_TRACKER.md`，明确本次探索目标与假设。
2. **开发期**：在 Cursor 中创建新分支或脚本。Markdown 允许你左侧写代码，右侧开笔记，实现“代码与文档”同步。
3. **沉淀期**：将结果对接回追踪器，记录结论。若方案成熟，重构并合并进 `main_pipeline.py`；过时构思移入 `archive/`。

## 5. 关键原则 (Rules of Thumb)
- **只加不删**：原始构思存入 `archive/` 而非删除，保留历史上下文。
- **严禁覆盖**：运行不同实验时，输出到独立文件夹（如 `results/2026-04-28_exp1/`）。
- **文档先行**：修改代码前，先用 Markdown 写清楚理由。
