# 高强度使用半年cursor，经验&踩坑分享给你！

> **@你的AI背包** · [原文](https://www.xiaohongshu.com/discovery/item/699c33a3000000000e03f3b7?source=webshare&xhsshare=pc_web&xsec_token=ABzT8IixEYDnsbr4TKyxqexSkppYPTlCSos3NIakbDtFQ=&xsec_source=pc_share)

## 要点

1. **Agent 与 Ask 分场景**：需求已想清楚、要改代码跑测试时用 Agent（规划→找文件→写码→测）；还在构思方案、只想读全库逻辑时用 Ask，避免 AI 过早生成执行计划、推理变慢或乱改代码。
2. **项目第一天写 `.cursorrules`**：把技术栈、命名、代码规范写进全局 Prompt，从源头锁工程标准；社区有各语言框架模板可改。但 rules 不宜过长——复杂业务逻辑放 `docs/` 的 Markdown，需要时用 `@` 引用，防止挤占上下文导致 Prompt 疲劳。
3. **每次指令 `@` 相关文件**：明确「只改这几个文件」，避免 context 一长 AI 自作主张改别处引入新 bug；作者习惯多花两秒 @ 文件，省半小时 debug。
4. **Composer 做多文件联动改**：函数签名/返回值跨多文件时，用自然语言描述变更（如「返回格式从 A 改 B」），Agent/Composer 一次改全调用点，比全局搜索手工改漏改少；作者曾一次改前端+后端+库+配置四层。
5. **配置 MCP 扩能力**：通过 Model Context Protocol 让 Agent 访问网页、数据库、Notion/Jira 等，Cursor 从编辑器升级为工作流智能体（如学术助手自动搜论文而非手抄）。
6. **改 bug 前先让 AI 写测试**：标准流程——(1) 为当前正常功能写通过测试锁边界；(2) 写复现 bug 的失败用例定终点；(3) 再修到全绿，避免修 A 坏 B 的逻辑泥潭。
7. **原子化 Git 提交**：每轮 Accept AI 改动后立即 `git commit`；可让 Cursor「总结当前变更并 commit+push」，乱改时可精确回退到任意完好时刻。
8. **避坑：上下文膨胀与模型滥用**：对话/@ 文件过多、窗口占用超 50% 会「降智」（忘指令、重复代码、回退刚修 bug）；每完成独立功能单元就关窗开新对话。模型分层——攻坚用 Claude Opus/GPT Codex；日常开发用 Sonnet/Gemini Pro；测用例/UI/格式化用 Flash/Mini/Haiku。纯靠 AI 堆代码会技术债爆炸，需同步更新 `.cursorrules`、让 AI 写关键注释、每周 Agent Code Review 去冗余。

## 正文

用了半年 Cursor，我从“代码搬运工”变成了“独立开发者”。踩了无数坑之后，我总结了一套使用方法论——4个基础经验 + 3个进阶技巧 + 3个血泪教训。
这不是一篇无脑鸡汤文，只是一个半年老用户的实战手册。

💡 核心经验简介
• 选对模式： 想清楚了用 Agent 跑自动化；没想清楚用 Ask 聊思路。
• 规矩先行： 第一天就写 .cursorrules。核心规范留里面，业务逻辑丢 docs/，防止 AI “降智”。
• 精准引用： 养成用 @引用 相关文件的习惯。锁死修改范围，拒绝 AI 乱改出 Bug。
• 进阶黑科技： 配置 MCP 连通全网论文/数据，Cursor 就不只是代码工具，而是你的全能 Agent。
• 拒绝乱改： 遇到 Bug 先让 AI 写测试用例。有了边界，AI 才不会在逻辑泥潭里反复横跳。
• 原子提交： 每一轮改完立即 Git Commit。AI 乱改不怕，一键回退到任何“完好时刻”。
⚠️ 2026 最新避坑指南
• 防止降智： 窗口占用超 50% 必开新对话。定期“断舍离”，保持 AI 注意力集中。
• 模型分层（省钱 SOP）：
• 攻坚： Claude 4.6 Opus / GPT-5.3 Codex (逻辑最稳)。
• 主力： Claude 4.6 Sonnet / Gemini 3.1 Pro (性价比之王)。
• 体力活： Gemini 3 Flash / GPT-5 Mini (测用例、改 UI 绝配)。
